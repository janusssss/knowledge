# 怎么做延迟消息
Kafka 本身并没有原生的延迟消息功能，但可以通过多种方式来实现延迟消息。
可以利用时间轮TimingWheel来做实现

# 缓解消费压力
缓解消费压力主要有这几类手段：

**1. 横向扩展（最核心）**
- **增加分区数**：分区是 Kafka 并行度的上限。先扩分区，才能让更多消费者真正并行消费。
- **增加组内消费者数**：分区数 >= 消费者数时，每个消费者负责若干个分区，吞吐量近似线性提升。

**2. 消费端调参**
- `max.poll.records`：调大单次拉取的记录数，减少 RPC 次数。
- `fetch.min.bytes` / `fetch.max.wait.ms`：批量拉取，积攒一定数据或等待时间再返回，提高吞吐。
- `session.timeout.ms` / `max.poll.interval.ms`：调大后避免频繁 rebalance。
- `enable.auto.commit` 关闭 + 手动提交，配合异步处理，减少提交阻塞。

**3. 消费逻辑优化**
- **多线程消费**：单消费者拉取后交给线程池并发处理（注意分区顺序和事务边界）。
- **异步处理**：把耗时的下游调用改为异步/消息队列，消费线程不阻塞。
- **批量写入**：下游 DB/缓存使用批量 insert、批量发送，减少 IO 次数。

**4. 处理慢与堆积**
- **拆分业务**：不同业务用不同消费组 + 独立 Topic，互不拖累。
- **消费者内部分流**：按 key 哈希分到多个子队列分别处理。
- **削峰**：消费跟不上时，先落库/暂存，再异步逐步消费（本地缓存、Redis 缓冲等）。

**5. 数据链路优化**
- 消息压缩（`compression.type`）减少网络/存储开销。
- 增大 broker 的 `fetch` 相关参数，加快拉取。

**关键原则**：并行度 = min(分区数, 消费者数)，所以扩容消费压力时，**分区数要提前规划够**。如果分区已经满了，先扩 Topic 分区（需注意 key 顺序和重新均衡的成本），再水平加消费者即可。

# 角色关系
## 一、一个极简的地图

```
                生产端                          存储端                              消费端
         Producer → Broker(存数据)                       ← Consumer
                 Topic (=一个频道)                        Group(业务)
                   分成多个 Partition(=多列货架)          一个组内多个 Consumer
                   每列货架自动编号 Offset(=取件号)        每个消费者负责几列货架
```

## 二、名词逐个解释

| 名词 | 一句话理解 | 类比 |
|------|-----------|------|
| **Broker** | 一台存消息的服务器 | 仓库 |
| **Topic** | 一类消息的通道 | 一个频道（如"订单"、"日志"） |
| **Partition** | 一个 Topic 切成多条道，Kafka 并行度的来源 | 通道内分出多列货架 |
| **Offset** | 某条消息在某分区里的顺序编号 | 货架上的取件号 |
| **Producer** | 发消息的一方 | 快递员 |
| **Consumer** | 拉消息、处理消息的一方 | 收货分拣员 |
| **Consumer Group** | 一组干同样活的消费者 | 一个分拣班组 |
| **Leader/Follower** | 每个分区的"主/从副本"（冗余备份） | 主货架 + 备份货架 |
| **Rebalance** | 增删消费者后重新分活 | 班组人员变了重新分工 |

## 三、关键关系（你问过的都在这里）

**1. Topic ⊃ Partition**
一个 Topic 有 1~N 个分区，消息按 key/轮询写入各个分区。分区越多，写入和消费的并行度越高。Offset 是**在分区内部编号**的，不是全局编号。

**2. Partition → Group 内的一个 Consumer（一对一，动态绑定）**
- 同一个分区，同一时刻只被**一个 group 内**的一个消费者消费。
- 消费者可以同时吃多个分区；一个消费者挂了，它占的分区立刻被别人接管（rebalance）。

**3. 并行度公式**
```
消费吞吐上限 = min(分区数, 组内消费者数)
```
所以："想加消费者"必须先保证"分区够用"，两者要和割让。

**4. Group ↔ Topic 多对多**
- 一个组可以订阅多个 Topic；一个 Topic 可以被多个组订阅。
- 不同组各自消费全量、offset 独立 → "同一个业务别开多个组（会各自消费一遍），不同组就是不同业务/不同消费语义"。

**5. 一组一业务 ≈ 实践准则**
- 组 = 独立消费进度 + 独立分区分配 + 独立需求语义
- 同一个业务加吞吐 → 组内加消费者（扩分区）
- 不同业务各自消费同一份数据 → 开不同的组

## 四、一条完整链路串一遍

> 订单服务(Producer) 把订单消息发到 Topic `order`（有 6 个分区 P0~P6）。
> 数据被存到某 broker 的各分区货架上，每个分区按顺序编号（offset）。
> 组 `order-handler` 里有 3 个消费者，rebalance 后每人负责 2 个分区，
> 各自从自己的分区按 offset 往下拉消息做处理，每处理完就提交 offset。
> 老板想更高效 → 把分区扩到 9 个、组里加到 9 个人，吞吐就上来了。
> 这时候预警系统想监控订单 → 另开一个组 `order-alert`，它自己消费全量,不影响上面。

一句话收尾：**Topic 定义"是什么"，Partition 定义"多快"，Consumer 定义"谁在干"，Consumer Group 定义"干这个活的一群人"，Offset 定义"干到哪了"。**

# kafak生产者吞吐量降低，怎么排查问题
producer 吞吐本质是批次有效载荷除以（攒批等待 + RTT + broker 处理 + 落盘），哪一项先到上限，吞吐就卡在哪。我的第一步是用 JMX
  把它劈成客户端和服务端两半。」

  ## 第一层，客户端

  producer 是异步流水线，吞吐掉的头号原因是有人把它改成了同步。

  - linger.ms=0 是默认值，也是很多压测案例吞吐腰斩的直接原因，一条消息一个请求，RTT 和请求头的固定开销远大于消息本身
  - batch.size 和 linger.ms 是一对，前者是字节上限后者是等待上限，谁先满足谁发车。batch.size 小而消息大，批次永远装不满，等于把 linger.ms 白给
  - buffer.memory 是攒批的总池子，池子打满 send() 就阻塞在 max.block.ms 上。这三个参数有配比关系，随手调一个只是把瓶颈挪个位置
  - 压缩是拿客户端 CPU 换带宽，gzip 或高 level 的 zstd 能直接把 CPU 打满
  - max.in.flight.requests.per.connection 调到 1 换保序，等于串行发请求，开幂等之后上限是 5
  - 代码里 send().get()、循环里 flush()，最容易忽略但杀伤力最大

  证明是攒批的问题，看 request-rate 和 records-per-request：请求数暴涨而每请求记录数掉，就是批次碎了。

  ## 第二层，分区和 key

  分区数是并行度的硬上限，一个分区只能落在一条 IO 线程上，分区数少于 broker 数就是浪费机器。反过来给太多会涨端到端延迟和 rebalance
  时长，没有免费午餐。

  key 倾斜是另一半，一个热 key 落一个分区其余空转，看分区级的 BytesInPerSec 一眼就露。key 为 null 时走 sticky
  partitioner，把批次钉在一个分区上攒满再换，比早期轮询省请求。

  ## 第三层，broker

  这层最能加分，因为能扯到底层设计。Kafka 吞吐高的根基是顺序追加写、依赖 page cache 而不是自己管刷盘、sendfile 的 zero-copy 让数据从磁盘到 socket
  不经过用户态。

  那它什么时候塌：page cache 被别的进程挤掉、盘快满了、JBOD 上某块盘拖后腿、num.io.threads 和 num.network.threads 不够、broker 自己 GC。指标看
  RequestHandlerAvgIdlePercent 和 NetworkProcessorAvgIdlePercent，这俩往下跌就是真处理不过来。

  ## 第四层，副本和 acks

  acks=all 的吞吐取决于最慢那个 follower。UnderReplicatedPartitions > 0 或者 ISR 频繁收缩，写入就在等副本同步，num.replica.fetchers
  在多分区机器上经常是隐形瓶颈。这是吞吐与可靠性的正面权衡点，面试官很喜欢在这追问。

  ## 第五层，外部

  网络（带宽、跨机房 RTT、丢包重传、TLS）、配额（quota.producer.default
  被设过特别容易忘）、集群运维动作（扩容、分区重分配、滚动升级）期间数据在网络上搬家。

  ## 收尾必须给判断方法，不能只甩清单

  先分「突然掉」还是「渐变」：突然掉优先怀疑集群事件、配额、下游流量变化；渐变就怀疑数据量增长、分区不均、磁盘劣化。再拿 kafka-producer-perf-test
  用相同参数跑基线，把客户端环境和集群问题劈开。原则是先观测再动手，别靠改参数碰运气。

  追问的话还有两个可选：一是 4.0 之后只有 KRaft，controller 抖动影响的是元数据路径，produce
  路径感知不明显；二是批次调大提吞吐但会推高尾延迟，这是必然代价。

# JMX怎么使用
Kafka 的指标通过 JMX 的 MBean 暴露，本地用 jconsole 或 Kafka 自带的 JmxTool 直接读，生产上挂 jmx_exporter 转成 Prometheus 指标长期采集。
