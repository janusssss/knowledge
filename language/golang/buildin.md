# slice
## 结构
```go
type slice struct {
    array unsafe.Pointer // 指向底层数组的指针
    len   int            // 当前切片的长度（当前元素的个数）
    cap   int            // 当前切片的容量（底层数组的总长度）
}
```
## 扩容机制
1. 计算新容量
	- 如果当前容量（oldCap）小于 256，新容量（newCap） = 旧容量 * 2。
	- 如果当前容量大于等于 256，则按照公式 `newCap = oldCap + (oldCap + 3*256) / 4`增长，这大约是 1.25 倍到 1.375 倍 的增长率，随着容量增大，增长率会逐渐降低并向 1.25 倍收敛

2. 内存对齐修正：计算出初步的 newCap 后，Go会根据切片的元素类型（et.size）进行内存对齐。它会向上取整到某个合适的内存大小级别，目的是为了优化内存分配和管理。
内存对齐的常见级别：8, 16, 32, 48, 64, 80, 96, 112, 128, 144... 字节。

3. 最终容量确定：最终容量就是经过内存对齐修正后的值。

# map
## 结构
map的底层是一个哈希表，主要由 hmap（哈希表结构体）和 bmap（桶数组）两个核心数据结构组成。
其中hmap负责管理整个map的元数据（如长度、扩容状态、种子），
而bmap则是实际存储键值对的内存桶，每个桶可以容纳8个键值对，并在溢出时链接额外的溢出桶。


- hmap：这是 map 的头结构，包含了 map 的核心元信息。
	- 元素数量计数器
	- 桶数量的对数（决定了桶数组大小是 2^B）
	- 指向桶数组和旧桶数组的指针（用于扩容）
	- 哈希种子
- bmap：这是真正的存储桶，每个桶：
	- 可以存储最多 8 个键值对
	- 有一个 tophash 数组，存储键哈希值的高8位，用于快速定位
	- 键值对是分开紧凑存储的（早期是交错存储）
	- 通过溢出指针连接成链表，解决哈希冲突

## 扩容机制
- 增量扩容 (翻倍)：当负载因子 >6.5（即平均每个桶装了超过6.5个元素）时触发。
这会创建一个两倍大小的新桶数组，目的是降低哈希冲突，保证操作的高效性。
	1. 分配一个大小为原来两倍（B = B + 1）的新 buckets 数组。
	2. 将 hmap.buckets 指向新数组，将 hmap.oldbuckets 指向旧数组。
	3. 将 hmap.nevacuate 设置为 0，表示迁移从 0 号桶开始。
	4. 后续对 map 的插入和删除操作时，会渐进式地将 oldbuckets 中的键值对重新哈希并分散到新的两个桶中（X 和 Y，规则是 hash & (2^B) == 0 的去 X，否则去 Y）。这个过程不是一次性完成的，避免了巨大的瞬时延迟。

- 等量扩容 (整理：当溢出桶过多但负载因子不高时触发。这通常发生在大量增删后，它创建同样大小的新桶数组，目的是整理碎片、释放空的溢出桶，优化内存和遍历性能。
	1. 分配一个和旧 buckets 同样大小的新 buckets 数组。
	2. 步骤与增量扩容类似，但目的是整理和压缩。将旧的、稀疏的桶（尤其是因为大量删除造成的）中的键值对紧凑地排列到新桶中，并回收多余的溢出桶，从而提升访问效率。

# interface
interface定义了一组方法的集合。接口的内部实现机制是Go语言运行时系统的一部分，它允许程序在运行时动态地确定一个值是否实现了某个接口，并调用相应的方法。Go 的接口实现依赖于两个核心概念：类型信息和方法表。 

- 类型信息（Type Information）：
指向一个描述接口所要求的类型（具体实现接口的类型）的元数据结构。这个元数据包含了类型的名称、方法集等信息。
- 数据指针（Data Pointer）： 
指向实际存储的值。这个值必须实现了接口所要求的所有方法

实现细节
1. 空接口： 
	interface{} 是一个特殊的接口，它不包含任何方法。因此，任何类型都可以隐式地实现 interface{}。空接口的内部结构与普通接口类似，但它不包含任何方法信息，只有类型信息和数据指针。
     
2. 方法表（Method Table）： 
    当一个类型实现了接口中的所有方法时，Go 运行时会为该类型生成一个方法表（method table）。方法表是一个函数指针数组，每个指针指向该类型实现的接口方法。
    当接口变量被赋值时，Go 会检查赋值给接口的值是否实现了接口的所有方法。如果实现了，Go 会将该类型的类型信息和方法表与接口变量关联起来。
     
3. 类型断言（Type Assertion）： 
	类型断言允许你从接口变量中提取出具体的值。Go运行时会检查接口变量中的类型信息是否与你断言的类型匹配。
	如果匹配，它会返回该类型的值；否则，会引发 panic（除非使用了“comma ok”形式，如 val, ok := iface.(Type)）。
 
4. 接口转换： 
    当一个接口类型的值被赋给另一个接口类型时，Go会检查源接口的类型是否实现了目标接口的所有方法。
    如果是，赋值成功；否则，编译失败

# sync.WaitGroup实现
    WaitGroup 底层维护了一个 计数器（原子操作）和信号量。

        Add() 原子地增加或减少计数器

        Done() 减少计数器，等价于 Add(-1)

        Wait() 检查计数器，如果不为 0，就通过信号量阻塞当前 goroutine

    当计数器归零时，Add() 会通过 runtime_Semrelease 唤醒所有等待的 goroutine。整个过程依赖 原子操作 保证并发安全，用 信号量 实现阻塞和唤醒。核心是状态存储在 state1 字段，高32位存计数器，低32位存等待者数量，并用 noCopy 防止复制。"

    "常见用法是主 goroutine 等待多个子 goroutine 完成，比如并发处理任务后收集结果。使用时要注意 Add 必须在启动 goroutine 前调用，避免和 Wait 并发调用。"


# channel底层实现

**“channel 底层是 `hchan` 结构体，核心有三块：**
 1. **环形队列**存数据；
 2. **两个等待队列**（sendq/recvq）存阻塞的 Goroutine；
 3. **一把互斥锁**保证并发安全。

 **发送和接收的逻辑分三种情况：**
 - 如果对方队列有等待者，**数据直接拷贝**给对方，不走缓冲区；
 - 否则如果缓冲区有空位，就**入队**；
 - 否则当前 Goroutine **被挂起**，加到等待队列里。

 **关闭时**会唤醒所有接收者，给零值；但再发送会 panic。

 这个设计用 **Goroutine 阻塞** 替代了传统多线程的复杂锁，是 Go CSP 模型的底层实现。”

# 内存分布
🧠 一、基本概念：Go 的堆 vs 栈
|特性|   栈（Stack）|   堆（Heap）
|---|---|---|
|归属|   每个 goroutine 独享|   所有 goroutine 共享
|生命周期|   随函数调用自动分配/释放|   由 GC（垃圾回收器）管理
|分配速度|   极快（指针移动即可）|   较慢（需 runtime 分配 + 锁竞争）
|容量|   初始约 2KB，可动态扩容至几 MB|   几乎无限（受限于虚拟内存）
|是否触发GC|   ❌ 否|   ✅ 是
|典型存储内容|   局部变量、函数参数、返回地址 |  逃逸对象、大对象、跨 goroutine 共享数据

```bash
┌─────────────────────────────────────────────────────────┐
│  goroutine                                             │
├─────────────────────────────────────────────────────────┤
│  栈 (stack)64操作系统 最大 1GB                                   │
│  ├── 函数调用帧                                        │
│  ├── 局部变量（小对象，编译器确定大小）                 │
│  ├── 函数参数、返回值                                  │
│  └── 逃逸到堆的指针引用                                │
├─────────────────────────────────────────────────────────┤
│  堆 (heap) 无上限（受系统内存限制）                    │
│  ├── make([]byte, 2<<32)  ← 8GB 在这里               │
│  ├── new 出来的对象                                    │
│  ├── 动态分配的大对象                                  │
│  └── 逃逸分析的变量                                    │
└─────────────────────────────────────────────────────────┘
```

# recover()
## Panic 可捕获性完整对照表

| Panic 类型 | 触发路径 | 可捕获 |
|-----------|---------|--------|
| **显式 panic()** | `runtime.gopanic()` | ✅ 可以 |
| **数组/切片越界** | `runtime.gopanic()` | ✅ 可以 |
| **空指针解引用** | `runtime.gopanic()` | ✅ 可以 |
| **nil map 写入** | `runtime.gopanic()` | ✅ 可以 |
| **类型断言失败** | `runtime.gopanic()` | ✅ 可以 |
| **向已关闭 channel 发送** | `runtime.gopanic()` | ✅ 可以 |
| **关闭已关闭的 channel** | `runtime.gopanic()` | ✅ 可以 |
| **关闭 nil channel** | `runtime.gopanic()` | ✅ 可以 |
| **整数除零** | `runtime.gopanic()` | ✅ 可以 |
| **log.Panic()** | `runtime.gopanic()` | ✅ 可以 |
| **并发 map 写入** | `runtime.fatal()` | ❌ 不可以 |
| **并发 map 读写** | `runtime.fatal()` | ❌ 不可以 |
| **栈溢出** | `runtime.fatal()` | ❌ 不可以 |
| **死锁** | `runtime.fatal()` | ❌ 不可以 |
| **内存耗尽（OOM）** | `runtime.fatal()` | ❌ 不可以 |
| **SIGSEGV（段错误）** | 操作系统信号 | ❌ 不可以 |
| **SIGBUS（总线错误）** | 操作系统信号 | ❌ 不可以 |
| **log.Fatal()** | `os.Exit(1)` | ❌ 不可以 |
| **os.Exit()** | `os.Exit()` | ❌ 不可以 |
| **向 nil channel 接收**（阻塞） | `runtime.fatal()` | ❌ 不可以 |
| **运行时调度器错误** | `runtime.fatal()` | ❌ 不可以 |

---

## 判断规则

```
✅ 走 runtime.gopanic() 路径 → 可以捕获
❌ 走 runtime.fatal() 路径   → 不可以捕获
❌ 走 os.Exit() 路径         → 不可以捕获
❌ 走操作系统信号路径         → 不可以捕获
```


## 面试标准回答

> **Go 里的 panic 只有一种，就是走 `runtime.gopanic()` 这个路径的，它是可以被 `recover()` 捕获的。**
>
> **其他三种情况：`runtime.fatal()`、`os.Exit()`、操作系统信号，它们根本就不是 panic，所以 `recover()` 捕获不到。**
>
> **判断标准很简单：看错误输出的第一行。以 `panic:` 开头的是真 panic，可以捕获；以 `fatal error:` 或 `signal` 开头的，不是 panic，捕获不到。**

---

## 展开说明（面试加分项）

### 1. `runtime.gopanic()` —— 真 panic
- 显式调用 `panic()`
- 运行时错误：数组越界、空指针、类型断言失败、关闭已关闭的 channel 等
- 走标准 panic 链，会执行 defer，可被 recover

### 2. `runtime.fatal()` —— 致命错误，不是 panic
- 并发 map 读写、栈溢出、死锁、内存耗尽
- 直接终止程序，不执行 defer，无法 recover
- 错误信息以 `fatal error:` 开头

### 3. `os.Exit()` —— 主动退出，不是 panic
- `log.Fatal()` 底层就是调用 `os.Exit(1)`
- 直接退出进程，不执行 defer，无法 recover

### 4. 操作系统信号 —— 硬件/系统级异常，不是 panic
- SIGSEGV（段错误）、SIGBUS（总线错误）
- 由操作系统发出，不走 Go 的 panic 机制，无法 recover

---

## 总结金句

> **能 recover 的才是 panic，不能 recover 的根本不是 panic。**
