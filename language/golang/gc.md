Go 的 GC 是非分代、非移动、并发三色标记-清扫，核心设计目标是低延迟而不是高吞吐，
所以它的停顿被压到极短，但代价是内存不主动还给 OS。

---

# gc步骤
0. Mark setup（STW，极短）
   - 上一轮清扫收尾（sweep termination）
   - 打开写屏障
   - 准备根集合

1. 并发标记
   - 并发扫描根：goroutine 栈、全局变量、finalizer、堆指针
   - 三色：白（未确认）→ 灰（待查）→ 黑（确认存活）
   - 混合写屏障
   - 后台标记 + Mark Assist

2. Mark termination（STW，很短）
   - 关闭写屏障
   - 处理残余灰色对象
   - 不重扫栈（Go 1.8+）

3. 清扫（并发 + 懒）
   - 白色对象变空闲
   - 后台 scavenger 慢慢归还 OS

# 混合写屏障
  - shade(*slot) = 删除屏障（Yuasa），防止旧对象唯一引用被删后漏标。
  - shade(ptr) = 插入屏障（Dijkstra），防止黑对象指向白对象。
  - 栈上写入不加屏障（性能原因），所以栈灰色期间才需要额外 shade 新指针。

# 为什么 Go 1.8 不用重扫栈
1. 栈扫描一次后变黑，不再扫；
2. 混合写屏障保证栈黑后，新写入不会引入白对象；
3. 新分配对象默认黑色（alloc black）——这是混合屏障的硬性前提！

Go 1.8 之前，栈是 permagray，每次 GC 结束都要 STW 重扫栈，这是最大的停顿来源。
1.8 引入混合写屏障 + 新对象默认黑，消除了栈重扫，STW从毫秒级降到几十微秒。

# Mark Assist（辅助标记）
 - 不是“进度慢了才触发”，而是按分配债务记账；
 - 每个 goroutine 分配越多，欠的标记工作越多；
 - 欠债超标，必须先帮 GC 标记才能继续分配。

 GC 不是等标记进度落后再拉人，而是每个 goroutine 按分配量记账，谁分配多谁先停下来帮工。

 # 触发时机：分配驱动，不是定时
触发阈值 = 上次 GC 后存活内存 × (1 + GOGC/100)

- GOGC=100 表示内存翻倍才 GC；
- 待机、不分配 → 可能永远不 GC；
- GOMEMLIMIT（Go 1.19+）是软上限，接近限制时 GC 会更积极。

# 内存归还不是 GC 的事，是 scavenger 的事
- GC 干的事：垃圾 → 空闲页
- scavenger 干的事：空闲页 → 还给 OS（madvise）
  - scavenger 后台异步、低优先级、节流运行；
  - 目标是降到某个“估计 RSS”而不是归零；
  - Go 1.16+ 默认 MADV_DONTNEED，1.12–1.15 默认 MADV_FREE（内核懒回收，RSS 下降更慢）。

我线上观察过一个服务：高峰申请 10G，待机后 RSS 慢慢降，这是因为 scavenger 在后台渐进归还，不是定时 GC。

# 不要依赖 GC 释放内存
- GC 不跑，垃圾一直占堆；
- GC 跑了，内存也未必还给 OS；
- 干完活长待机，应该 runtime.GC() + debug.FreeOSMemory()，或设 GOMEMLIMIT。

# scavenger
Go runtime 里那个 scavenger，管的是把堆里空闲 span 的物理内存还给操作系统。
GC 负责回收对象，scavenger 负责把已经不用的页 madvise 掉，让 RSS 降下来。但它不会全还——留一部分，因为刚还回去又要分配就得吃 page fault，反而更亏。
保留比例跟 GC 后的堆目标挂钩，所以 GOGC 和 GOMEMLIMIT(1.19+) 会间接影响它干活。
Go 1.16 之前它是定时醒来慢慢扫，之后改成分配路径主动唤醒，按需工作。想看它有没有干活，带 GODEBUG=scavtrace=1 跑一下就行。

| 追问 | 一句话回答 |
|---|---|
| 为什么不重扫栈？ | 混合屏障 + 新分配对象默认为黑，栈扫描一次后就是黑的，不会藏白对象 |
| 为什么会有浮动垃圾？ | 并发标记期间新分配对象虽然默认黑，但可能本来就是垃圾，要下一轮才清 |
| Go 是分代吗？ | 不是，非分代、非移动，优点是不用处理对象搬移和写屏障代际问题 |
| 为什么 STW 能这么短？ | 1.5 并发标记，1.7 栈屏障，1.8 混合写屏障消除栈重扫，剩下的 mark setup/termination 都是微秒级收尾 |
| 什么场景 GC 频繁？ | 分配量大、存活内存翻倍快；可以用 GOGC 调大降低频率，但峰值内存会更高 |
| 你怎么观测 GC？ | `GODEBUG=gctrace=1` 看触发时间/停顿；`GODEBUG=scavtrace=1` 看归还量；runtime metrics 看 HeapReleased |
