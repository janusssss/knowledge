systemd的启动文件（Unit File）主要由三个核心部分构成，它们通过不同的参数来定义服务的行为、依赖关系和安装方式。这些参数全部定义在文件的各个“小节”（Section）中。

下面是每个部分中一些最常用的核心参数。

### 📄 [Unit] 小节：定义元数据与依赖关系

这个小节包含所有服务都通用的信息，主要用于描述服务、管理文档以及建立单元之间的依赖与启动顺序。

| 参数 | 作用 | 关键说明 |
| :--- | :--- | :--- |
| **`Description=`** | 服务的简短描述 | 会显示在 `systemctl status` 等命令的输出中，最好用通俗易懂的语言描述，如 "Apache2 Web Server"。 |
| **`Documentation=`** | 文档链接 | 可以指定 `man:`、`https://` 等格式的URI，方便查询服务文档。 |
| **`After=` / `Before=`** | 启动顺序 | 定义单元间的启动先后顺序，**不隐含依赖关系**。例如 `After=network.target` 表示在网络服务启动后再启动当前服务。 |
| **`Requires=`** | 强依赖 | 当前服务启动时，会**同时启动**列表中的单元。若这些单元启动失败，当前服务也可能启动失败。 |
| **`Wants=`** | 弱依赖 | `Requires=` 的弱化版。列表中的单元会被尝试启动，即使失败也不会影响当前服务的启动，是更推荐的依赖配置方式。 |
| **`BindsTo=`** | 绑定依赖 | 比 `Requires=` 更强。如果绑定的单元意外停止，当前服务**也会被停止**。常与 `After=` 结合使用，以确保服务在依赖项准备好之后才启动。 |
| **`Conflicts=`** | 冲突关系 | 定义冲突的单元。启动当前服务会自动停止列表中正在运行的服务，反之亦然。 |

### ⚙️ [Service] 小节：定义服务启动行为

这个小节是 `.service` 类型文件的核心，专门用于定义如何启动、管理和停止服务。

| 参数 | 作用 | 关键说明 |
| :--- | :--- | :--- |
| **`Type=`** | 服务启动类型 | **最关键的参数之一**，告诉 systemd 如何判断服务已成功启动。常用类型包括：<br>- **`simple`** (默认)：主进程一启动，就认为服务已就绪。<br>- **`forking`**：服务会通过 `fork()` 创建子进程后父进程退出。**传统UNIX守护进程常用此类型**，通常需要配合 `PIDFile=` 使用。<br>- **`oneshot`**：一次性任务，主进程退出后即完成任务。常与 `RemainAfterExit=yes` 搭配以保持active状态。<br>- **`notify`**：服务通过 `sd_notify()` 主动发消息通知systemd自己已就绪，适合需要精确控制的复杂服务。 |
| **`ExecStart=`** | 启动命令 | 指定启动服务时要执行的**绝对路径和命令**，如 `/usr/bin/npm start`。 |
| **`ExecStop=`** | 停止命令 | 指定停止服务的命令，如果不指定，systemd 会发送 SIGTERM 信号来终止进程。 |
| **`ExecReload=`** | 重载命令 | 指定重载服务配置的命令，如 `kill -HUP $MAINPID`。 |
| **`PIDFile=`** | PID文件路径 | 当 `Type=forking` 时**强烈推荐设置**，systemd通过此文件读取服务主进程的PID以进行管理。 |
| **`RemainAfterExit=`** | 退出后保持状态 | 当设为 `yes` 时，即使服务进程全部退出，systemd 也认为该服务仍处于“active”状态。**常用于 `Type=oneshot` 的服务**。 |
| User | 启动用户 | |
| Group | 启动组 | |

### 📦 [Install] 小节：定义安装与启用行为

这个小节定义了如何使用 `systemctl enable` 或 `disable` 命令来安装服务，主要控制服务的自启动行为。

| 参数 | 作用 | 关键说明 |
| :--- | :--- | :--- |
| **`WantedBy=`** | 依赖当前服务的单元 | **最常见**的安装参数。`WantedBy=multi-user.target` 表示当系统进入多用户模式时，会尝试启动当前服务，**是实现开机自启的标准配置**。 |
| **`RequiredBy=`** | 强依赖当前服务的单元 | 与 `WantedBy` 类似，但依赖关系是强制的，如果当前服务启动失败，依赖它的单元也会受影响。 |
| **`Also=`** | 附属单元 | 在启用或禁用当前服务时，也同时启用或禁用列表中的其他单元。 |

### 💡 核心参数详解：`Type=`

`Type=` 是 `[Service]` 小节中最关键的参数之一，它直接影响 systemd 如何判断服务的启动状态。官方文档建议，对于长时间运行的服务，应优先考虑 `simple`、`exec`、`notify` 或 `dbus` 类型。

-   **`simple` (默认值)**：最快速，主进程一被 fork 出来 systemd 就认为启动成功。适用于大多数无需复杂初始化的服务。
-   **`forking`**：适用于传统的 UNIX 守护进程，启动后父进程退出。必须配合 `PIDFile=` 让 systemd 找到真正的守护进程。
-   **`notify`**：最精确，服务自己通过 `sd_notify()` 发送 "READY=1" 消息告知 systemd 已完全就绪。**适用于有复杂初始化流程、且需要确保启动完成后才开始后续任务的服务**。

### 💎 总结与最佳实践

1.  **文件结构**：一个标准的 systemd service 文件通常包含 `[Unit]`、`[Service]` 和 `[Install]` 三个核心小节。
2.  **依赖关系**：建议优先使用 **`Wants=`** 而非 `Requires=`，以避免因某个非关键依赖失败导致整个服务无法启动，使系统更健壮。
3.  **启动类型**：对于大多数新编写的服务脚本，**`Type=simple`** 是简单场景下的好选择；如果服务启动耗时较长或需要精确控制启动状态，**`Type=notify`** 是更专业的选择。
4.  **启用与自启动**：若想让服务开机自启，需要在 `[Install]` 小节中设置 **`WantedBy=multi-user.target`**，然后执行 `systemctl enable <服务名>`。

由于 systemd 的参数非常丰富，除了上述核心参数，还有大量用于定义执行环境（`systemd.exec(5)`）、资源限制（`systemd.resource-control(5)`）和进程终止方式（`systemd.kill(5)`）的参数可供探索。如果你想深入了解某个特定参数，可以随时再问我。
